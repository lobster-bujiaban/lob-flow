# LOB Flow 实施计划

## 1. 要掌握的系统是什么

AI 应用平台不是一个工作流画布，而是配置管理、模型网关、运行引擎、知识库、工具系统、发布入口和治理能力的组合。

```text
                     ┌→ Model Provider / LLM
App Draft → Publish → Runtime → Knowledge Retrieval
      │                  │    └→ Tool / Agent
      │                  ↓
      └→ Version      Events / Trace
                         ↓
                 Web App / API / Logs
```

本项目先实现一条可运行的纵向链路，再扩展节点类型和平台能力。每个阶段都同时关注领域模型、调用链、状态变化、失败路径和验收证据。

## 2. 与系列其他项目的边界

| 项目 | 深入研究内容 | LOB Flow 中的定位 |
|---|---|---|
| `lob-harness` | Agent Loop、会话、工具执行与沙箱 | 复用 Agent 运行概念，不重复实现编码 Agent |
| `lob-vector` | Chunk、Embedding、向量数据库与混合检索 | 通过检索接口接入，重点学习平台侧知识库生命周期 |
| `lob-graph` | Checkpoint、中断恢复、并行与子图 | 本项目实现够用的调度能力，深层状态机原理留给专题项目 |
| `lob-mcp` | MCP 协议、能力协商与企业工具网关 | 本项目先实现统一 Tool Adapter，后续再接 MCP |
| `lob-observe` | Trace、Prompt、评测与成本分析 | 本项目生成标准运行事件并完成基础观测 |

## 3. 核心领域对象

```text
Workspace
  ├─ Member / Role
  ├─ ModelProvider / Credential
  ├─ KnowledgeBase
  ├─ ToolProvider
  └─ App
      ├─ DraftDefinition
      ├─ PublishedVersion
      └─ Run
          ├─ NodeRun
          ├─ Event
          └─ Artifact
```

需要始终区分三类状态：

- 编辑态：用户正在修改、允许不完整的 Draft。
- 发布态：不可变、可审计、可回滚的 Version 快照。
- 运行态：一次请求的输入、节点状态、输出、错误和消耗。

## 4. 分阶段实施

### 阶段 0：AI 应用领域模型与最小 Chat App

目标：不做画布，先打通“创建应用—配置 Prompt—输入问题—得到回答”的最小闭环。

任务：

1. 定义 Workspace、App、Draft、PublishedVersion、Run 和 Message。
2. 支持 System Prompt、用户输入模板和模型参数配置。
3. 实现本地假模型，保证无网络也能重复验证运行链路。
4. 保存应用草稿、运行输入、输出、状态和错误。
5. 提供 CLI 或最小 API 完成创建、运行和查看记录。
6. 输出 `run_started`、`message_delta`、`run_succeeded`、`run_failed` 事件。

验收：同一个应用可以连续运行多轮；每次运行拥有独立 ID 和完整事件；失败不会产生伪造的成功结果。

必须理解：领域配置与运行状态的边界、流式内容与最终消息的关系、应用级配置如何进入一次模型请求。

### 阶段 1：模型网关与流式运行

目标：用统一协议接入不同模型供应商，并安全管理凭据和调用指标。

任务：

1. 定义 `ModelProvider`、`ModelConfig`、`CredentialRef` 和统一请求响应协议。
2. 接入 OpenAI-compatible 真实供应商，应用不提供 Fake Model 运行路径。
3. 统一处理流式文本、结束原因、Token Usage、超时和供应商错误。
4. 支持模型参数校验、默认值和供应商能力声明。
5. 凭据加密或引用保存，接口与日志只返回脱敏状态。
6. 实现超时、有限重试和错误分类，避免对不可重试错误盲目重放。

验收：业务运行层不依赖具体供应商 SDK；切换模型只修改配置；断流、限流、鉴权失败和超时均有明确状态与事件。

### 阶段 2：工作流定义、校验与 DAG 调度

目标：实现最小工作流引擎，理解图定义如何转换成可执行计划。

任务：

1. 定义 Workflow、Node、Edge、Port 和 NodeType。
2. 实现 Start、Template、LLM、Answer 四类节点。
3. 校验唯一入口、节点引用、端口连接、必填配置和不可达节点。
4. 实现拓扑排序、依赖满足判断和节点调度。
5. 定义统一 Node Executor 输入、输出、上下文和错误结构。
6. 记录工作流级与节点级事件，流式输出能映射到对应节点。
7. 发布时生成不可变定义快照，运行只引用版本快照。

验收：可执行 `Start → Template → LLM → Answer`；循环依赖或断裂边在运行前被拒绝；修改 Draft 不影响已发布版本。

### 阶段 3：变量系统、控制流与可靠执行

目标：让工作流从直线链路扩展为可表达真实业务逻辑的可靠执行图。

任务：

1. 建立系统变量、应用输入、节点输出、环境变量和 Secret 的命名空间。
2. 实现类型校验、变量引用解析、模板插值和敏感值脱敏。
3. 增加 If/Else、并行分支、聚合节点和有限迭代。
4. 明确分支未命中、节点跳过和空输出的传播语义。
5. 支持节点超时、重试、失败分支和工作流取消。
6. 保存关键运行状态，使进程重启后能识别未完成运行；恢复执行只对幂等节点开放。
7. 为外部副作用节点设计幂等键，避免恢复或重试造成重复操作。

验收：至少完成一条含条件和并行分支的流程；失败分支可复现；取消后不再启动新节点；重试不会重复产生已保护的副作用。

### 阶段 4：知识库检索与 RAG 节点

目标：把知识库作为平台资源接入工作流，而不是把检索逻辑写死在应用中。

任务：

1. 定义 KnowledgeBase、DatasetDocument、Segment、IndexingJob 和 RetrievalResult。
2. 实现文档上传、解析、分块、索引状态和失败记录。
3. 通过统一 Retriever 接口接入 `lob-vector` 或外部向量存储。
4. 增加 Knowledge Retrieval 节点，支持 TopK、阈值、Metadata Filter 和引用信息。
5. 将检索结果作为结构化变量传给 LLM 节点。
6. 输出答案引用并能定位到文档、Chunk 和原文位置。
7. 处理重建索引、删除文档、版本变化与运行一致性。

验收：上传固定文档后可发布一个带引用的问答应用；无证据问题明确拒答；文档越权或跨 Workspace 检索被阻止。

### 阶段 5：工具、Agent 与人工介入

目标：让应用安全调用外部能力，并理解 Workflow 与 Agent 两种编排方式的差异。

任务：

1. 定义 Tool Provider、Tool、JSON Schema、CredentialRef 和执行结果。
2. 实现 HTTP 工具和一个本地确定性工具。
3. 增加 Tool 节点，支持参数映射、超时、重试和结构化错误。
4. 实现最小 Agent Loop：模型选择工具、执行、回传结果并继续推理。
5. 设置最大步数、Token/成本预算和工具白名单。
6. 对高风险工具增加人工确认、中断状态和恢复入口。
7. 保存每次工具提案、审批决定、参数和结果审计记录。

验收：同一工具可被固定 Workflow 节点和 Agent 动态调用；拒绝审批后不会执行工具；达到预算或步数上限时可靠终止。

### 阶段 6：版本发布、API、权限与多租户

目标：完成从内部调试工具到可被真实用户调用的平台闭环。

任务：

1. 实现 Draft 校验、发布、历史版本、回滚和下线。
2. 提供调试入口、已发布 Web App 与服务 API 三种运行来源。
3. 为 API Key 建立哈希存储、作用域、轮换、吊销和调用审计。
4. 实现 Workspace Owner、Admin、Editor、Viewer 等最小 RBAC。
5. 所有 App、知识库、工具、凭据和运行查询强制带 Workspace 边界。
6. 增加速率限制、输入大小限制和并发配额。
7. 明确删除应用、知识库和成员后的数据保留策略。

验收：未发布草稿无法从生产 API 调用；旧版本可回滚；跨 Workspace ID 枚举无法读取或运行资源；被吊销 Key 立即失效。

### 阶段 7：可观测、评测与生产化

目标：能够定位一次 AI 应用为什么慢、贵、失败或回答不正确。

任务：

1. 为 App Run、Node Run、模型请求、检索和工具调用建立统一 Trace 关联。
2. 记录首 Token 延迟、总延迟、Token、模型成本、节点耗时和错误类型。
3. 提供按 App、版本、状态和时间过滤的运行记录。
4. 支持 Prompt、输入、输出和敏感变量的分级脱敏与保留策略。
5. 建立固定样例集，对不同版本执行回归评测。
6. 增加队列、Worker、并发控制、优雅停机和僵尸运行回收。
7. 验证数据库迁移、备份恢复和 Worker 中断后的行为。

验收：给定一次异常运行，能从 Trace 定位到具体节点和外部调用；版本发布前可运行最小评测集；服务重启不会把未知状态误报为成功。

### 阶段 8：Dify 源码映射与最终差异清单

目标：从“会使用概念”提升到“能定位源码并解释实现取舍”。

任务：

1. 固定研究的 Dify 版本、许可证和仓库提交。
2. 定位应用创建、草稿保存、发布和运行的 API 入口。
3. 追踪一次 Chat App 与 Workflow App 的完整后端调用链。
4. 映射图定义、变量池、节点执行、事件流和运行持久化相关模块。
5. 映射模型供应商、知识库、工具、权限与凭据管理入口。
6. 为每条主链路记录“Dify 源码对象 → LOB Flow 对象 → 差异与原因”。
7. 形成未实现能力、刻意简化项、风险与后续路线清单。

验收：至少完成创建并发布应用、运行工作流、知识检索、工具调用四条源码调用链；每条链路均包含入口、核心对象、状态变化和最终持久化位置。

## 5. 推荐模块边界

```text
src/lob_flow/
  app/             应用、草稿、版本与发布
  model_gateway/   模型供应商、凭据与统一协议
  workflow/        图定义、校验、调度与节点执行器
  runtime/         Run、事件、取消、重试与恢复
  knowledge/       知识库资源与 Retriever 接口
  tools/           工具注册、执行、审批与审计
  auth/            Workspace、成员、角色与 API Key
  observability/   Trace、指标、成本与运行查询
  api/             调试、管理和生产调用入口
```

依赖方向保持单向：入口负责鉴权和参数转换，应用服务负责编排，核心领域对象不依赖 Web 框架、模型 SDK、向量数据库或任务队列。

## 6. 每阶段记录模板

每完成一个阶段，至少记录：

- 本阶段可运行入口与固定演示输入。
- 核心对象及其状态变化。
- 一次成功调用链与一次失败调用链。
- 数据保存位置和事务边界。
- 新增事件及其顺序。
- 超时、取消、重试、恢复或幂等行为。
- 与 Dify 对应概念的映射及差异。
- 已知限制和下一阶段需要解决的问题。

## 7. 学习完成标准

完成本项目后，应能独立回答并通过代码或运行记录验证：

1. 为什么 Draft、PublishedVersion 和 Run 必须分开建模。
2. 模型网关如何隔离供应商差异与凭据。
3. 工作流图如何校验、调度并产生可消费的流式事件。
4. 条件、并行、重试和恢复如何影响节点状态与副作用。
5. 知识库和工具如何作为 Workspace 资源安全地被应用引用。
6. Workflow 与 Agent 分别适合什么任务，如何控制 Agent 的风险与成本。
7. 发布、回滚、API Key 和 RBAC 如何共同保护生产应用。
8. 如何从 Trace 判断问题来自 Prompt、模型、检索、工具还是调度器。
9. Dify 对应主链路位于哪些源码模块，自研实现做了哪些简化以及为什么。
